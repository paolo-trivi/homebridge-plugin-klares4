# F2 — Matter names, rename, commands

## Config keys

None added, renamed or removed.

## Changelog entries (2.3.0)

### Fixed
- Renaming a Matter accessory (a name changed on the panel, a `matterOverrides` name, a name collision resolved at the end of the first sync) no longer removes the accessory from the bridge and adds it back: the name is changed on the live accessory, which keeps its identity, so controllers keep rooms, favourites and automations. The old remove-and-add path is only a fallback when the new name does not show up, and it now keeps the accessory's identity too. (MAT-04)
- A light that turns out to be a dimmer is still replaced once by a dimmable accessory (Matter cannot change a device type in place), but the new accessory keeps the identity of the old one. (MAT-04)
- Covers commanded from Apple Home, Alexa or Google no longer show as already open/closed the moment the command is sent: the accessory keeps the position the panel reports, shows the requested target and shows the cover as opening or closing until it has moved. Automations on "cover closed/open" no longer fire at the command. (MAT-05)
- A brightness command on a dimmer that is off no longer reaches the panel (the controller does not switch the light on for it either). (MAT-08)
- A Matter command arriving while the panel connection is not available fails visibly in the controller instead of being reported as done. (MAT-15)
- The Matter name list (`klares4-matter-names.json`) no longer expires 30 days after its last write: names of devices still on the panel never expire, and a removed device's name is kept for 30 days after it was last seen. Previously an installation restarted at least once a day lost the whole list after 30 days. (MAT-06)
- The Matter name list is written atomically and a list written by a newer plugin version is left untouched after a downgrade. (MAT-11)
- Matter names with characters outside the Basic Multilingual Plane (some symbols, rare scripts) are shortened the way Homebridge counts them, so two accessories can no longer end up with the same truncated name, and a character is never cut in half. Very long names in the configuration or in a `.ksa` backup no longer block Homebridge for seconds. (MAT-12)
- An out-of-range or non-numeric value restored from an old Homebridge cache no longer makes a Matter accessory fail to register for the whole session, and is no longer shown as a reading (0 °C, NaN, 21 °C for a thermostat fallback); the controller shows the value as unknown until the panel reports it. (MAT-13)
- The voice-name analysis at the end of each sync is much faster on large installations. (MAT-16)

- A device deleted on the panel no longer keeps its Matter name as if it still existed until Homebridge restarts: its name stays reserved for 30 days from the last time the panel listed it. (MATTER-RC1-04)

## Migration notes
- No change to UUIDs, config keys or MQTT topics. The persisted Matter name list keeps its format (version 2); existing files are read as they are.
- A name list file left by 2.2.0 with rows older than 30 days is now loaded entirely (2.2.0 discarded them): devices still on the panel keep their names.
- A rename made by this version on a brand-new accessory (first start, name collision) can log once, from Homebridge, `Cannot update Matter accessory <id> - not found in cache`: Homebridge has not saved its cache yet. It is harmless: the new name is on the accessory and persists across restarts (matter.js stores `nodeLabel`), and Homebridge's cache record is rewritten with the new name at the next start.

## Documentation notes
- `docs/MATTER_TROUBLESHOOTING.md` / ARCHITECTURE: renames no longer go through unregister/register; the finalizer reads `bridgedDeviceBasicInformation.nodeLabel` from the endpoint and writes it in place (`MatterTopologyCoordinator.renameInPlace`), then `updatePlatformAccessories`. Unregister + register (with `uniqueId` restored through `restoreUniqueId`) only when the label is not observed, and for the dimmer upgrade. The "rooms/automations survive because the endpoint identity is UUID-derived" wording is wrong: what matters to controllers is `uniqueId`, now kept.
- Name length: the Matter limit (32) is counted in UTF-16 code units, like Homebridge and matter.js (`homebridge/dist/matter/server/AccessoryManager.js:808-818`, `@matter/node/dist/cjs/behavior/state/validation/constraint.js:162`). HAP names still count characters (64).
- Name list lifetime: names of devices on the panel never expire; reservations of devices no longer on the panel last 30 days from when they were last seen.
- Matter covers: after a command from Matter, `current` stays the last position reported by the panel, `target` is the requested one and the movement status is opening/closing; it returns to stopped when the panel reports the cover at the target.

## Known limits (Homebridge, not fixable with the public API)
- **LevelControl `stepWithOnOff`, `moveWithOnOff`, `stopWithOnOff`** (R8). Homebridge's `HomebridgeLevelControlServer` overrides only `moveToLevel`, `move`, `step`, `stop` and `moveToLevelWithOnOff` (`homebridge/dist/matter/behaviors/LevelControlBehavior.js:20, 50, 76, 102, 128`); the three others run matter.js's default implementation, which changes the Matter level/on-off state without calling any plugin handler, and the public API offers no state-change subscription (`StateManager.notifyStateChange` emits only with monitoring enabled, `homebridge/dist/matter/server/StateManager.js:316-321`). Effect: a controller that uses them (none of Apple Home, Alexa or Google is known to, for a plain dimmer) changes the Matter state while the panel does nothing; the next panel status puts the state back. Only Homebridge can fix it (route the three commands to handlers).
- **Device type change** (OnOffLight → DimmableLight): matter.js fixes the device type when the endpoint is built and Homebridge refuses a register of a UUID live in this session (`AccessoryManager.js:164-169`; only an endpoint restored from its cache is rebuilt, `:157-162`). The upgrade stays unregister + register; the new endpoint gets the previous `uniqueId` back by a state write, the same identity Homebridge keeps in its own "changed structure" path. Verified on the real stack, also across a restart (`test/matter-rename-in-place.test.js`). The endpoint is absent from the bridge for the time of the replacement (about 1 s with the settle below).
- **Unregister settle (1 s) kept.** The report suggests 0 when the unregister call resolves; that is correct on Homebridge 2.5 (the call awaits the close) but not on 2.4, where the endpoint already reads as absent while closing and a register in that window is refused. The plugin cannot tell the two apart without a version check, so the settle stays; it now only applies to the fallback and to the dimmer upgrade. The absence is confirmed again after the settle.
- `productLabel` is not rewritten in place (only `nodeLabel`, the name controllers show); Homebridge sets it from the cached `displayName` at the next start.

## Integration after the merge of release/2.3.0 (I, G, A, F1, B, K, H, E)

Done in F1's and E's files, at the coordinator's request:
- **Dimmer upgrade logged as `[upgrade]`**, not `[rename]`: `MatterRegistrationFlow.register(device, { reason, inheritUniqueId })` (`matter-registration-flow.ts`); `logRegisterRequested` takes `reregister: 'rename' | 'upgrade'`.
- **Identity across endpoint replacements**, one mechanism: `matter-endpoint-replacement.ts` (`replaceEndpoint(reg, coordinator, kind)`) removes the old endpoint and records `reg.inheritedUniqueId`; `completeRegistration` gives it back once the new endpoint answers (`coordinator.restoreUniqueId`). Used by the stale-endpoint purge (`matter-registration-recovery.ts`), E's second Thermostat payload (`matter-thermostat-attempts.ts`), the rename fallback and the dimmer upgrade (both now pass the id to the flow instead of restoring it themselves).
- **Decision on the TemperatureSensor fallback: new identity.** A replacement keeps `uniqueId` only when the new endpoint is the same device with the same function (same shape, another payload of the same device type, a rename, OnOffLight → DimmableLight, a superset). Thermostat → TemperatureSensor (and the reverse, the recovery of a persisted fallback) changes the function: a controller that kept the identity could keep scenes and automations that set a temperature on what is now a read-only sensor, or keep a sensor's room/automations on a thermostat. A new identity makes the controller show a new accessory, which is what E's migration note already tells users. Homebridge itself keeps the identity on any "changed structure" (AccessoryManager.js:157-162), so this is a plugin choice, documented here. Verified on the real stack (`test/matter-endpoint-identity.test.js`): purge keeps it; on Homebridge 2.5 the 2.2.0 Thermostat payload is refused by matter.js (no endpoint, nothing to keep) and the fallback sensor gets a new id; the second payload keeping the id is shown with the fixture (which accepts it).
- **One probe-cluster rule**: `declaredClusters(accessory)` in `matter-topology-coordinator.ts` (declared clusters without the `bridgedDeviceBasicInformation` key Homebridge writes into the plugin's `clusters` object; the bridged info only when nothing is declared). `isMatterAccessoryQueryable` (F1) and `registrationProbeCluster` both use it.
- **Unregister settle as a timing**: `MatterTimings.unregisterSettleMs` (default 1000, env `KLARES4_MATTER_UNREGISTER_SETTLE_MS`, 0 allowed), passed by the registry to the coordinator's constructor; a coordinator built directly still reads the env. Test with the fixture's close window (`unregisterCloseMs: 20`) and settle 0: two finalize passes in a row produce no "already registered".
- `test/fixtures/hb-matter-api.js` models `uniqueId` (random for a new endpoint, kept by a restored one and by its "changed structure" rebuild, writable through `bridgedDeviceBasicInformation`, carried by `cacheSnapshot()`). Additive.
- Thermostat temperatures: E's mapper now gives `null` for a missing room temperature; no caller of `toMatterTemperatureCelsius` passes a missing value any more (`matter-value-guards.ts` checks first; the setpoint default in E's mapper is a setpoint, not a reading). `toCentidegrees` (the 2.2 re-export from the mapper) keeps the `fallbackC = 0` signature but has no caller in `src/`.

## rc.1 review follow-up
- **Flaky `matter-endpoint-identity` test, cause in the code.** `completeRegistration` set `registered` and only then awaited the uniqueId restore, whose write Homebridge applies on a later turn (`StateManager.js:103`); under load a reader could see the replacement registered under its new random identity. The coordinator now applies the inherited `uniqueId` inside the register operation itself (`inheritOnNextRegister`, set by `replaceEndpoint`, the rename fallback and the dimmer upgrade), after waiting for the endpoint to exist (on 2.4 register returns first), so nothing sees the endpoint before its identity is the old one; the flow's restore after the probe stays as a check. A test asserts the identity at the moment of the "registered" log line.
- **E / registration path (not touched, request):** `completeRegistration` (`matter-registration-flow.ts`) can still mark `registered` before its own `restoreUniqueId`; with the coordinator applying the identity at register time this is now only the fallback for a runtime whose endpoint appears after the observation budget. Moving the restore before `reg.status = 'registered'` would close it entirely.
- **MATTER-RC1-01:** `test/fixtures/hb-matter-api.js` has `semantics: '2.4' | '2.5'` (default `'2.5'`). On `'2.4'` register resolves at once and the endpoint is built later (`registerBuildMs`), unregister resolves while the endpoint is still closing (UUID still held). F37 (`matter-registration-race.test.js`) runs on both with an explicit settle of 150 ms against a close of 80 ms, plus a test that shows "already registered" on 2.4 with settle 0. Rename fallback, dimmer upgrade, second Thermostat payload and double finalize run on both semantics. The real 2.4 job (task K / harness owner) still has to cover settle and rename fallback on a real 2.4 stack.
- **MATTER-RC1-04:** `DeviceEventRouter.matterSnapshots` returns only the devices reported (discovery or status) since the current sync started; `SyncLifecycle` resets it at each login and takes the list when the sync completes, for the queued name pass.
- **MATTER-RC1-07:** a same-device replacement whose old endpoint shows no `uniqueId` logs a warning (`[Matter] <id>: the endpoint being replaced shows no uniqueId ...`).
- **MATTER-RC1-02 (not done, E's files):** the automatic/explicit recovery of a persisted TemperatureSensor fallback (`resolvePersistedThermostatFallback`) unregisters the sensor without reading its `uniqueId`; if the Thermostat is refused again the sensor comes back with a new identity. Fix for E: read the sensor's `uniqueId` before that unregister, keep it on the registration, and let `registerFallbackAccessory` replace as `same-device` when the previous endpoint was the sensor.
- **NEW-1 (regression from MAT-05):** the cover position refresh after a Matter command no longer calls `updateAccessoryState` from its own timer; it goes through the registry's state-update queue like every other push (`CommandContext.queueState` → `MapperDeps.queueState` → `MatterRegistrationFlow.queueState`, which merges it into the registration's pending updates per cluster and schedules the flush; a later panel status replaces it). Minimal pass-through added in `matter-registration-flow.ts` (`mapperDeps().queueState` and the 9-line `queueState`). Measured on Homebridge 2.5 (`test/matter-command-bursts.test.js`): this alone does **not** close the window. Cover commands 0 ms and 1 ms apart still end in "Cannot lock" for the 2nd..nth command (the panel receives them), 5 ms passes or fails depending on timing; lights and dimmers (no plugin push after a command) pass at 0/1/5 ms once the registration's own state pushes are done; a light command that lands while any plugin push is in flight (initial flush, realtime status) fails the same way, so the light tests wait for the pushes to drain and the general case is E's fix. The three cover burst tests are `todo` until task E's per-endpoint serialization of plugin pushes against commands (`matter-state-update-queue.ts`) is merged; they must then be enabled and pass.
