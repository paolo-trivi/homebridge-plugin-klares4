# Review of 2.2.0 and how 2.3.0 answers it

Public summary of a full read-only review of `homebridge-plugin-klares4` 2.2.0 (14 November 2026), written without any data from a real installation: it states what was found by area and how 2.3.0 resolves it. It describes the code as it was at the time; the current behavior is in [`docs/en/`](../en/README.md) and [`docs/it/`](../it/README.md), and the user-facing list of changes is in [`CHANGELOG.md`](../../CHANGELOG.md).

## Scope and method

Six review areas ran in parallel against `v2.2.0`: WebSocket client and protocol; platform, HomeKit, persistence and KSA import; security and privacy; thermostats; Matter; tests, documentation and quality. Nothing was sent to a panel or to a broker: behavior was reproduced against a simulated panel, a fake broker, and the real Homebridge Matter stack running without a network. Each finding was marked as **reproduced**, **deduced from the code** (call path verified) or **hypothesis**, with a confidence level.

122 findings: 5 High, 27 Medium, 71 Low, 19 Info; no Critical. The core held up: command correlation, PIN masking, TLS gating, the refusal of arming scenarios and the isolation of Matter-only names. What the review changed was the margin around those policies.

## The five main risks and their resolution

| Risk found in 2.2.0 | Resolution in 2.3.0 |
|---|---|
| **Thermostats on Homebridge 2.5**: the native Matter Thermostat never registered (the plugin sent preset attributes the runtime refuses), and the documented recovery could not succeed | The Thermostat declares only the attributes of what the output can do; a second attempt with the payload of 2.2.0 precedes the fallback; thermostats saved as a fallback get one automatic attempt; contract tests run against the real Homebridge Matter stack |
| **Fail-open exposure**: outputs of unrecognized categories (sirens, alarm bridges, indicators, irrigation) became commandable lights; a scenario with a missing or unknown category could run with the stored PIN | Exposure is fail-closed: only recognized categories are exposed; the rest is opt-in per device (`exposeOutputs`, `exposeScenarios`); arming scenarios are never exposed; the command service refuses anything that is not a discovered device of that kind |
| **Thermostat writes from a stale cache**: a setpoint wrote back the whole configuration read at login (switching heating back on, dropping a program); the displayed temperature could be the panel's board temperature; the degraded routing could write to another thermostat | Partial writes in the form of the official app (mode only, or the active season's block after a fresh read); fail-closed routing; the board temperature only as a last resort; reconnections no longer replay the old configuration |
| **Privacy**: the debug file that the plugin invited users to share held the home position and the account; the error reporter hooked the module loader of the whole Homebridge process and its scrub was not recursive | Telemetry removed entirely, with its dependency; the debug file is confidential, `0600`, and masks position, sunrise and sunset, account, serial numbers and panel identifier at any depth |
| **Matter topology and release process**: devices deleted on the panel stayed forever in the controllers; after a panel outage cached endpoints looked reachable; tests used a mock with the semantics of an older Homebridge; the stable release was not the build validated as a release candidate | Prune after three syncs, also across restarts and without restarting Homebridge; reachability published on cached endpoints after 15 s; the mock follows Homebridge 2.5 and real-stack contract tests were added; the release workflow requires a published release candidate with the same dependencies and separates build from publish |

## Findings by area

### WebSocket client and protocol

- *Found:* a frame was handled in one `try/catch` (one bad entry dropped the rest); refused discovery or realtime reads were ignored and the sync reported complete; command queues had no deadline, so commands could go out late; a state already held could confirm a command; invalid values (`NaN`, `"false"`) became commands; inbound frames were not checked (shape, CRC, size); logins that kept failing were retried too eagerly in some cases and stopped for good in others; sensor values out of range were clamped into plausible readings; PIN masking missed some shapes.
- *Resolved:* per-device isolation; sync that fails on refused reads and reconnects with backoff, 60-second watchdog; per-device queues with a deadline, `latest-wins` and `reject-while-busy` policies; confirmation only by a transition observed after the command; strict validation; inbound frame check; login guard with one attempt per hour after three failures; invalid values discarded; masking at any depth.

### Platform, HomeKit, persistence and KSA

- *Found:* one failing device could stop others from registering; the KSA import replaced hand-written thermostat mappings at every start; the HomeKit prune guard was ineffective on reconnects; `config.json` rewrites broke symbolic links and failed silently on single-file bind mounts; sensors never reported showed 0; files were created with the process umask; the `.ksa` file was trusted.
- *Resolved:* independent handling of HomeKit, MQTT and Matter per device; the import only adds what is missing; one prune discipline (families, 50 % floor, three misses) for HomeKit and Matter; atomic writes that keep links and fall back in place; "No Response" for unobserved sensors; `0600` for new files; the backup treated as untrusted input.

### Security and privacy

- *Found:* the findings of the main risks above, plus: MQTT had no authorization beyond the broker and no state-only mode; a broker password could reach the log; a malformed broker URL could connect elsewhere; an MQTT burst could keep the panel busy; MQTT clients could inject log lines; the support document did not match the code (supported versions, privacy claims).
- *Resolved:* `mqtt.commands`; the status topic with a last will; URL validation and masking; per-room command checks; command intake limits and quoting in the log; a current `SECURITY.md` with a private reporting channel.

### Thermostats

- *Found:* the partial-write problem above; ambiguous name matching between thermostats and sensors; spurious transitions at reconnect; heating and cooling outputs of one program acting on each other on Matter; echo of quick commands dropped as "already current"; a "cool" never confirmed moved later setpoints to summer.
- *Resolved:* the write forms, fail-closed routing, full-name matching only, role from program data, acknowledgement-confirmed values, season tracking that waits for the panel.

### Matter

- *Found:* renames and dimmer upgrades via remove-and-add (new identity, one-second absence); covers declared at their target position; unlimited retry of a refused endpoint; a name list that expired after 30 days of an always-restarted installation; names truncated in the middle of a character; a fallback store that rewrote files it did not understand.
- *Resolved:* rename in place; identity kept across replacements, except where the function changes on purpose; cover target and movement; probe that learns whether registration waits; names that never expire while the device exists, atomic writes; UTF-16-aware truncation; a conservative store.

### Tests, documentation and quality

- *Found:* the Matter mock modelled an older Homebridge; invariants (TLS gating, arming-scenario opt-in, PIN masking, command content) were not tested where they act; test fixtures held data from a real installation; tests left temporary directories and used fixed sleeps; the configuration schema, README tables and docs disagreed with the code (`logLevel`, `mqtt.port`, undocumented keys, stale roadmap, only-Italian titles); `ARCHITECTURE.md` named a third of the modules; `SECURITY.md` and the changelog guides stopped at 1.1.x.
- *Resolved:* real-stack contract tests, synthetic fixtures, no leftover directories; one validation point for the configuration with limits equal to the schema, and tests that tie schema, layout, runtime, README and docs together; the documentation rewritten in both languages; the changelog and migration guide brought up to date.

## What stays open

- Some behaviors were derived from captures that only show resting values and need confirmation on a real panel (refused login shape, bypassed and tamper zone values, thermostat notifications for keypad changes, cooling mode, unknown thermostat modes). They are listed in the release candidate notes and logged once when first seen.
- Logging levels: `logLevel` and `debug` still write at Homebridge's debug level; a logger wrapper that honors them is planned for a later release candidate.
- Limits that belong to Homebridge (some LevelControl commands, the unregister settle on 2.4) cannot be fixed with its public API and are documented in the [Matter page](../en/matter.md).
